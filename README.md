# Кредитный скоринг

Проект по построению модели кредитного скоринга для прогнозирования дефолта заёмщика в течение следующих двух лет.

В качестве основы используется публичный датасет **Give Me Some Credit**: около 150 тыс. наблюдений и 10 исходных признаков + бинарная целевая переменная.

Основной фокус проекта — не только обучение модели, но и полный ML-пайплайн:

* SQL-анализ данных;
* EDA и проверка качества данных;
* leakage-safe preprocessing;
* feature engineering;
* сравнение моделей;
* работа с дисбалансом классов;
* подбор threshold;
* оценка ROC-AUC / PR-AUC / KS;
* интерпретация модели через feature importance и SHAP.

---

## Датасет

**Целевая переменная:** `SeriousDlqin2yrs` — факт серьёзной просрочки / дефолта в течение следующих двух лет.

Для демонстрации работы с табличными данными исходный датасет был загружен в SQLite.

Использованы несколько SQL-паттернов.

### Базовая агрегация

Рассчитаны:

* количество наблюдений;
* средний возраст;
* общий default rate.

Результат:

### JOIN и оконная функция

Возраст был разбит на интервалы и присоединён к основной таблице через `JOIN`.

Для ранжирования дохода внутри возрастных групп использована оконная функция:

```sql

    PARTITION BY age_band
    ORDER BY MonthlyIncome DESC

```

При выполнении JOIN была обнаружена одна запись с `age = 0`, после чего она была удалена как некорректная.

### Группировка по возрасту

Default rate был рассчитан отдельно для возрастных групп:

| Возраст | Default rate |
| ------- | -----------: |
| 18–29   |       11.73% |
| 30–44   |        9.49% |
| 45–59   |        7.04% |
| 60–74   |        3.44% |
| 75+     |        2.01% |

В данном датасете наблюдается снижение **наблюдаемой** доли дефолтов при переходе к более старшим возрастным группам. Это описательная статистика и не интерпретируется как причинный эффект возраста.

| `Has90DaysLate`             | Индикатор наличия просрочки 90+ дней                   |

# 6. Кросс-валидация

После feature engineering проведено отдельное сравнение трёх моделей с использованием `StratifiedKFold` и двух метрик:

* ROC-AUC;
* PR-AUC.

| Модель              |             ROC-AUC |              PR-AUC |
| ------------------- | ------------------: | ------------------: |
| **CatBoost**        | **0.8638 ± 0.0040** | **0.3990 ± 0.0091** |
| LightGBM            |     0.8580 ± 0.0044 |     0.3890 ± 0.0076 |
| Logistic Regression |     0.8575 ± 0.0029 |     0.3568 ± 0.0072 |

CatBoost показал наибольшее среднее значение обеих метрик среди протестированных моделей.

При этом разница с LightGBM по ROC-AUC относительно небольшая, поэтому результаты рассматриваются как близкие по качеству, а не как принципиально разные.

# 8. Выбор порога классификации

Для получения бинарного решения threshold не фиксировался на стандартном `0.5`.

На validation set была построена Precision-Recall curve и выбран threshold, максимизирующий F1.

Результат:

```text
F1-optimal threshold = 0.790
```

На validation:

```text
Precision = 0.413
Recall    = 0.505
F1        = 0.454
PR-AUC    = 0.405
```

После выбора threshold он был зафиксирован и применён к test set.

Важно: `0.790` — это **F1-optimal threshold для данной validation выборки**, а не универсальный бизнес-порог.

В реальной кредитной системе threshold должен определяться с учётом стоимости ошибок, требований к recall/precision и других бизнес-ограничений.

## PR-AUC

```text

```

Baseline для PR-AUC при таком positive rate составляет примерно:

```text

```

Таким образом, PR-AUC модели существенно выше baseline, соответствующего доле положительного класса.


KS показывает максимальное абсолютное расстояние между эмпирическими распределениями model score для двух классов.

Это дополнительная метрика разделяющей способности, часто используемая в credit scoring.

Высокая статистическая значимость различия распределений сама по себе не является показателем качества модели, поэтому основное внимание уделяется самому KS и другим model metrics.

# 10. Model Score и калибровка

Поскольку финальная модель использует:

```python
auto_class_weights="Balanced"
```

значения `predict_proba` в текущей версии проекта следует рассматривать прежде всего как **model scores**, а не как окончательно откалиброванные вероятности дефолта.

Поэтому threshold `0.790` нельзя интерпретировать как:

> «клиент имеет 79% вероятность дефолта».

В дальнейшем можно дополнительно проверить калибровку model scores с помощью calibration curve и Brier score.

## SHAP-анализ

Для дополнительной интерпретации использован SHAP.

SHAP показывает:

* относительный вклад признаков;
* направление влияния конкретного значения;
* нелинейные зависимости;
* индивидуальные объяснения prediction.

Global SHAP importance в целом согласуется с CatBoost feature importance.

Особенно заметный вклад наблюдается у признаков, связанных с:

* credit utilization;
* delinquency history;
* возрастом.

SHAP-интерпретация показывает поведение **конкретной модели**, но не является доказательством причинно-следственной связи.

# 13. Основные результаты

### 1. Дисбаланс классов существенно влияет на выбор метрик

Положительный класс составляет около **6.68%**, поэтому accuracy не является основной метрикой.

PR-AUC позволяет лучше оценивать качество модели в условиях редкого положительного класса.

### 2. История просрочек является одним из наиболее информативных источников сигнала

Признаки, связанные с историей просрочек, входят в число наиболее важных факторов модели.

### 3. Feature engineering улучшает представление данных

Дополнительные признаки позволяют явно представить:

* совокупную историю просрочек;
* наличие серьёзной просрочки;
* взаимодействие utilization и delinquency;
* структуру кредитного портфеля.

### 4. Бустинговые модели хорошо работают с нелинейными зависимостями

CatBoost и LightGBM показывают более высокое PR-AUC, чем Logistic Regression.

При этом Logistic Regression после feature engineering остаётся конкурентоспособной по ROC-AUC.

### 5. Threshold и качество ранжирования — разные задачи

ROC-AUC и PR-AUC характеризуют качество ранжирования, тогда как threshold определяет конкретную точку на Precision-Recall trade-off.

Поэтому threshold должен рассматриваться отдельно от model ranking metrics.

# 14. Ограничения проекта

### Актуальность датасета

Give Me Some Credit — исторический публичный датасет и не отражает современный кредитный рынок.

### Отсутствие временной валидации

В проекте используется random stratified split.

Для production credit scoring предпочтительнее дополнительно проводить временную валидацию: обучаться на более раннем периоде и проверять модель на более позднем.

### Feature engineering

Не все engineered features обязательно дают прирост для каждой модели.

Например, interaction features могут быть более полезны для линейной модели, тогда как tree-based models способны самостоятельно находить многие нелинейные взаимодействия.
### Калибровка

Качество model scores дополнительно стоит проверить с точки зрения калибровки вероятностей.

### Мониторинг

После внедрения модели необходимо следить за тем, не изменились ли данные и качество модели со временем.
Можно мониторить:

- распределения признаков;
- распределение model scores;
- долю дефолтов;
- основные метрики модели.

Для этого могут использоваться, например, PSI и KS.

# 15. Возможные улучшения

## Оптимизация гиперпараметров

Провести систематический поиск гиперпараметров CatBoost / LightGBM с использованием Optuna.

## Калибровка вероятностей

Проверить calibration curve и Brier score и при необходимости применить:

* Platt scaling;
* isotonic regression.

## Бизнес-ориентированный подбор threshold

Подбирать threshold не только по F1, а через cost matrix.

Например, если false negative существенно дороже false positive, оптимальная точка разделения будет смещена в сторону большего recall.

## WOE и классический scorecard

Для классического credit scoring можно построить:

```text
Binning → WOE → Logistic Regression → Scorecard
```

Это позволит сравнить бустинги с более интерпретируемым scorecard-подходом, возможно использовать LR для большей обьяснимости.

## Временная валидация

Добавить временное разбиение для проверки устойчивости модели на более поздних данных.

## Внешние данные

Дополнительные внешние признаки потенциально могут улучшить predictive performance, однако их использование потребует отдельной проверки доступности, качества, leakage и стабильности во времени.
